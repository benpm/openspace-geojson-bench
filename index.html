GeoJSON performance branch against OpenSpace master

Measured on 24 November 2026

Every test below was run on two builds of OpenSpace: current master, and the same commit with the branch feature/geojson-performance merged into it (pull request). Each video shows both runs side by side, with OpenSpace's own frame rate counter at the top left and the build's name at the bottom right of each half.

  • The branch passed all 22 tests. Master passed 11, failed 3 and did not finish 8.
  • On master the wind turbine file fills the GPU's memory; on the branch it loads. In all five tests that load 9,673 or more of its points, master's GPU memory was still climbing when the watchdog stopped the run at 10.5 GB, 45 to 94 s after launch. The runs were stopped there so that nothing could crash. The branch loads all 77,379 points from the show's panel in 8.0 s and then draws them at 240 to 420 fps (panel test, flight test).
  • Memory per point. With 968 points, master uses 1,270 MiB more GPU memory than the branch, 1.3 MiB per point, and draws at 184 fps against 543.
  • Small GeoJSON content is faster too. Small subsets: 50 fps on master, 403 on the branch. Colorado grid and turbines: 26 against 380, and master draws none of the layers.
  • The large line and polygon sets load on the branch only. The 22 grid, pipeline and solar layers are loaded in 11 s on the branch (22 s on the first run); master was still on its loading screen after 10 minutes, also with the solar polygons alone and with the panel's grid buttons.
  • Ordinary scenes are not slower. Four of the five scenes without GeoJSON work run within 2% of master's frame rate. The eclipse scene, which draws one GeoJSON path, is 16% faster on the branch.
  • The map layers kept drawing for 15 minutes on both builds: all 30 steps of the long run changed the picture, at the same frame rate on both.
  • A large file from outside the show. The 135 MB landslide file takes 74 s to load on master in both runs. On the branch it takes 46 s the first time and 6 s from the branch's cache the second time, and it is drawn at 84 fps against 27.
  • What the branch does not solve. The 135 MB landslide file needs 4.4 GB of memory on the branch against 2.5 GB on master, and after the load call returns OpenSpace stutters for 25 s (6.5 s on master). Enabling the solar polygons blocks OpenSpace for 13 s. With the solar polygons enabled, the frame rate is 326 fps over the Pacific, where few polygons face the camera, and 103 fps over Asia, against 735 fps without the layer; no polygon showed through the globe in the Pacific view. A fisheye window halves the frame rate with the turbine file (217 fps against 426).

Actions
  • React: next planet in focus N
    Makes the next planet the focus without moving the camera, which raises the FocusNodeChanged event.

    Flies to the node in focus. Coming within its approach distance raises the CameraFocusTransition event.

    Moves the camera out to 50 times the size of the node in focus, which is outside its approach distance.

    Flips UserProperties.LabReactEnabled, which the event actions check, and restores the planet trails when turning the reactions off.

Method

MachineNVIDIA GeForce RTX 5070 (12 GB), AMD Ryzen 5 3600, 32 GB RAM, Windows 11
BuildsMSVC, Release, both built on the day of the run with the same options
masterOpenSpace master at b2d3b8a642 (23 November 2026). Its videos are labelled bench-master@b2d3b8a642, the name of the local branch
branchthe same commit with feature/geojson-performance (608b58f3f8, 7 commits) merged into it; labelled bench-pr@efdd05be88
Window1280 × 720, vertical sync off, so frame rates are not capped by the display
  • Two runs. Each test is first run without recording, then again with recording. The videos, the charts and all numbers not marked "first run" come from the second. Both builds started the first pass with empty caches; a cache that tests share is filled by whichever test comes first on this page, so "first run" is a cold start only for what a test loads that no earlier test did. Runs that master was not expected to finish, the 15-minute test and the panel tests were made once, recorded.
  • Frame rate. A script that runs every frame measures the time since the previous frame. It agrees with the counter drawn by OpenSpace, which is the average over the last 128 frames. The average is frames divided by time, so a single long frame lowers it; the median is not affected by that. "1% low" is the frame rate of the slowest 1% of frames. Recording lowered the frame rate by 1 to 4% in a comparison of runs with and without it.
  • Scene load is the time from the log line that names the profile to the first frame of the scene. Load call is the time a call that adds a layer takes to return. Until it draws smoothly is the time from then (or from enabling a layer) until two seconds have passed without a frame longer than one second.
  • Memory is sampled once a second: the working set of the OpenSpace process, and the memory in use on the whole GPU, shown as the amount above the level before launch.
  • Did not finish means the run was stopped: after the time limit of the test (10 minutes for most), or by a watchdog when more than 10.5 GB of GPU memory was in use or less than 4 GB of system memory was left. The frame rates of such a run cover only the time before it stalled.
  • Passing. A test passes when its script reaches the end, the log has no error line and the test's own checks hold; these are listed with each test.
  • Limits. Each pair of runs was made once, on one machine. The globe's imagery is fetched from the network while a test runs, which moves frame rates by a few percent from run to run. The first version of the 15-minute test looked at a Colorado-only layer from views that do not show Colorado; it was corrected and run again, and the results here are from the second version.
